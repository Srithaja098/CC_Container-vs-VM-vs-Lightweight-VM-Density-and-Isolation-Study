# Experiment design

## Hypotheses

| ID | Testable hypothesis | Support | Contradiction |
| --- | --- | --- | --- |
| H1: density | With the same host and instance application size, containers place the most instances, lightweight VMs are next, and full VMs place the fewest. | The observed order is `container > lightweight_vm > full_vm`; the supplied earlier-run reference is 128 / 64 / 8 per host. | Any rank reversal, or equal counts that erase the predicted advantage. |
| H2: start-up | Fleet-ready time is determined by isolation level's boot delay and is nearly independent of requested fleet size when instances boot in parallel. Full VMs are slowest, lightweight VMs next, and containers fastest. | Within each level, ready time is stable across fleet sizes; level order matches the hypothesis. | Ready time grows materially with fleet size, or level order differs. Report requested and successfully created fleet sizes together. |
| H3: noisy neighbour | An 8x-demand neighbour increases victim slowdown for uncapped containers more than for capped lightweight VMs; pinned full VMs remain near their no-neighbour baseline. | Paired noisy/baseline slowdown ratios are above 1 for containers and closer to 1 for pinned/capped levels. The earlier-run reference is 1.00 / 1.95 / 1.03 for full VM / container / lightweight VM. | Ratios are near 1 for containers, pinned/capped levels are affected as much or more, or the ordering changes. |

The earlier-run figures above are comparison targets supplied in the request, not results generated by these files. Do not substitute them for the CSV output.

## Design table

| Experiment | Independent variables | Fixed parameters | Metrics | Repetitions | Evidence rule |
| --- | --- | --- | --- | --- | --- |
| Density | Isolation level; requested instance count is increased until a rejection occurs. | `SimConfig`; seed 42; same host and application size; fresh scenario for each candidate count. | Placed instances per host (only populated for a one-host config), total placed instances, first rejected id, instance footprint in MB. | 5 fresh sweeps per level. | Evaluate H1 by the per-host ordering. Report integer counts; do not infer significance from identical deterministic repeats. |
| Start-up | Isolation level; fleet size 1, 8, 16, 32, 64. | `SimConfig`; seed 42; fresh scenario for each point; no cloudlets. | Requested fleet size, successfully created instances, `getFleetReadyTimeS()` in seconds. | 5 fresh scenarios per point. | Evaluate H2 by within-level stability and between-level order. If requested exceeds created, retain and flag the row rather than treating it as a fully placed fleet. |
| Noisy neighbour | Isolation level (pinned, uncapped, capped) and neighbour absent/present. | 4 victims; each victim runs one 100,000-MI cloudlet over the configured vCPUs; neighbour has an 8x demand multiplier and a 1,000,000-MI cloudlet; seed 42; fresh scenario per condition. | Finished victim cloudlet count; mean `Scenario.slowdown(c)` over successful victims; paired noisy-to-baseline slowdown ratio. | 5 baseline and 5 neighbour scenarios per level, paired by repetition number. | Evaluate H3 using only successful victim cloudlets. Fewer than 4 finished victims invalidate that replicate's mean; never replace missing means with zero. |

### Repeatability and API notes

The current model has no randomized workload choices, so five runs at fixed seed 42 should repeat exactly. They are checks that fresh-scenario runs agree, not five independent observations and not a basis for confidence intervals. Keep `replicate` in the CSV so discrepancies remain visible.

CloudSim placement failures are only visible after the scenario runs. Therefore the density implementation tests successive candidate counts with a fresh scenario for each count. Fleet readiness comes directly from `getBroker().getFleetReadyTimeS()`. Slowdown uses only victim cloudlets with `Cloudlet.SUCCESS` and the scenario's `slowdown(c)` method.

### Start-up calibration question for Person 1

The current `StartupBroker` computes fleet readiness as the configured per-level delay because all instances boot in parallel. The present `SimConfig` values therefore predict 30.00 / 2.00 / 3.80 seconds (full VM / container / lightweight VM), while the supplied reference is 30.00 / 2.07 / 3.79 seconds for a 32-instance fleet. The experiment does not need a per-instance boot cost to measure the model as written. Person 1 should decide whether the reference discrepancy is rounding/run variation or whether the isolation model needs an explicit per-instance boot-cost term; do not tune Person 2's measurement code to manufacture the reference values.
